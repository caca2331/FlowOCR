# 当前默认值：是什么、凭什么、以及**量过之后没采纳的**

这是维护者的决策日志：日期与"owner"标的是裁定来源；结论与关键读数在这里，细节和量法在写作"x 计划 / x 报告"的不公开维护记录里。

这一页只回答三个问题，别的都在各自的文档里：

1. 跑 `build_tracks` / `run_ocr2` **不带参数**时是什么行为；
2. 每个非显然的默认**凭什么**是这个值（依据在哪、验证规模多大）；
3. 哪些想法**量过之后没有采纳**——这类结论和"做成了"一样重要，
   不写下来就会被反复重试。

## 采纳规则：改动凭什么进默认

**只有这一份**；入口文件的护栏、开发指南只指向这里。按顺序判，前一条不过就不看后一条：

1. **正确性优先于提速**（owner 2026-09-22）：流程可以提建议改，但不为提速牺牲提供正确性的设计（decode-buffer 计划）。
2. **先有等价性或质量证据**：
   * 不改产物：逐字节相同（复用判据的 `SCHEDULING` 档），或 owner 定的噪声级（`NOISE_EQUIV` 档）——
     ORT 资源 / 调度类旋钮对账过就可以直接进这一档、不用再问；改"读哪一帧 / 怎么读"的不算（owner 2026-09-23，[obs 复用判据](README.md#obs-复用判据)）；
   * 改产物：事件级对账、打字机真值（改提取层必过，owner 2026-09-23）、用途 2 命中集合三把尺，按三档报漏（[报数口径](../dev-guide/verification.md#报数口径)）；
   * 规模按"跑多长"分档（[跑多长](../dev-guide/verification.md#跑多长按证据强度分档owner-2026-09-08)）：`bash dev_tools/sampleset.sh quick` 是一般性改动的 30 分钟集；
     动默认路径，证据强度要和它当初进默认时相当。
3. **收益**：墙钟按差幅分档读（[墙钟](../dev-guide/verification.md#墙钟按差幅分档读owner-2026-09-05)）；**资源占用也是收益**——
   墙钟噪声档但 CPU / 显存 / 内存明显省的也值得翻（owner 2026-09-20），所以 A/B 墙钟和整棵进程树的 CPU 一起报。
4. **没有提升也可以采纳**（owner 2026-09-25）：性能 / 行为在噪声档，但逻辑上更合理更简洁（例：规则从按设备分叉变成一条，[§1.27](#127-ort-线程池不自旋--ort-spin-off2026-09-25-owner-定gpu--cpu-一样perf-nightly-0925-报告)），又不算过度设计的。
   要写清"更合理"在哪、代价是什么；第 2 条的证据照旧要有——放宽的只是"必须有提升"。
5. **默认值全局统一，不按素材分叉**。按设备（GPU / CPU）定的调度差异不算分叉，前提是不改读数（[§1.17](#117-rec-池同时两个在途--rec-inflight-22026-09-23decode-buffer)、[§1.27](#127-ort-线程池不自旋--ort-spin-off2026-09-25-owner-定gpu--cpu-一样perf-nightly-0925-报告)）；按游戏特化走按游戏补丁（owner 2026-09-11）。
   设计方向上的约束：不为单个病例加特判、不做 VLM 判读层。
6. **写下来**：翻了的默认在本页记一节（依据、验证规模、代价、回退）；量过没采纳的记进 [§3](#3-量过之后没有采纳的)；报 A/B 只写臂名（[§0](#0-报-ab-的数只准写臂名不准写默认-vs-xaudit-5)）。

## 0. 报 A/B 的数**只准写臂名**，不准写「默认 vs X」（audit-5）

"默认"是会变的。2026-09-08 把 `--main-band` 推进默认时，`SUFFIX` 为空的那条臂
**直接覆盖**了原来当基准的产物，于是三处文档里引的数当场数不回来了
（`hit_delta 1 2 3 4 5 --b=-b` 现在全 0——两条臂是同一份产物）。

规矩：

- 一条臂 = 一个 `SUFFIX`。**改默认之前，先把旧默认冻成一条命名臂**：
  ```bash
  FORCE=1 SUFFIX=-band0 BUILD_ARGS="--main-band 0" bash dev_tools/head2head.sh 1 2 3 4 5
  ```
- 文档里每一组 A/B 都写明**哪两条臂**（`-band0` → 默认臂），不写"默认 vs X"。
- `head2head.sh` 在 `SUFFIX` 为空时会打印**当前默认值的指纹**
  （`python src/flowocr/analyze/build_tracks.py --print-defaults`，也落一份 `tmp/h2h/defaults.txt`）：
  指纹变了 = 默认变了，日志里看得见。
- 臂名一旦写进文档就**不要再拿它跑别的参数**——臂名是产物的身份。

### 1.1 `--prefetch 4`（2026-09-09 加，原 0 = 串行）

**这条和上面三条不是一回事**：它不改产物，只改产物出现得多快，所以判据也不同——
不是命中/漏条，而是**逐字节相同**。

| | |
| --- | --- |
| 改什么 | 解码挪到后台线程，有界队列（深度 × 帧大小；1080p 深度 4 = 24 MB）喂给 det/rec |
| 等价性 | **三种编码（av1/vp9/h264）× 两个解码后端（cv2/ffmpeg）六条臂，观测行逐字节相同**；2026-09-10 又在**真窗口 5 分钟**上验了一次（2,720 行逐字节相同） |
| 收益 | 端到端 `wall_sec`：60 s 切片上 vp9 **1.19–1.24×**、h264 1.05–1.12×、av1（cv2 解码）1.05–1.20×（三个时间点）；**vp9 真窗口 5 分钟上 1.18×**（41.76 → 35.52 s） |
| 为什么能这么定 | 它只改"什么时候解码"，不改"解出什么"。逐字节相同**已经是最强的等价性证据**，比头对头更强——头对头是在产物不同时才需要的。**这也是它能绕过"阶段性结论要 120–240 分钟素材"那一档的唯一理由**：判据不依赖素材量 |
| 上限 | vp9 的 1.24× 已经贴着理论天花板 `1/(1-0.22)=1.28×`（2026-09-09 fps-and-rec-budget 报告的分账：那段 vp9 窗口上解码占 22%） |

### 1.2 `--decoder ffmpeg`（2026-09-10 改，原 `cv2`）—— **owner 决定，全局统一**

**和 `--prefetch` 不一样，它会改产物**，所以判据不是逐字节相同，而是命中与漏条。

| | |
| --- | --- |
| 改什么 | 采样帧改由 ffmpeg 子进程送进管道（`select` 只挑采样帧，跳过的帧不进 Python），纯软解（av1 走 `libdav1d`） |
| 质量 | 三段**有剧本**的 20 分钟窗口（f1/f4/f5，120 min 素材）全链 A/B：**命中集合差 +0 / +0 / +1、重复认领 0 → 0**。obs 层的差 94–100% 是单字符翻转、集中在 conf 0.25–0.37 的垃圾框上，没有一处把真台词读成别的台词 |
| 收益 | av1 端到端 **3.4×**（OpenCV 预编译包内置的 av1 解码器慢 12 倍）；vp9/h264 打平 |
| 为什么是**全局**默认 | owner："不想有的用 cv2 有的用 ffmpeg"。两种解码器的产物不逐字节相同，混用会让产物之间不可比 |
| 怎么保证不混用 | `framesource.DEFAULT_DECODER` 是唯一的常量；`run_ocr2` 的默认值和 `ocr_complete.obs_reusable` 的复用判据都读它——**旧默认产的观测不再算"已跑完"**，驱动脚本会重跑（守卫钉住了两处都读常量） |
| 验证规模 | 三段 20 分钟窗口 + av1 5 分钟窗口 |

**决定时已知、owner 接受的两条限制**（不是遗漏，是明知）：

1. **有分辨力的样本只有 n = 1 段**。f1 两臂的主轨都是垃圾（`'Dummy'` 26%、2,376 条/h），
   f5 也偏脏；只有 f4 干净，那里两臂 247 vs 248 条、命中完全相同。
   根因是 20 分钟窗口上"主轨 = 单个区域"的打分本来就不稳。
2. **`--decoder ffmpeg` 从没在整片规模（6 h）跑过**。子进程、stderr 解析线程、管道背压
   活一个多小时——结构性风险，和质量无关。**第一部整片跑完先看 `_meta` 的
   `stopped_early` / `complete`，再看分数。**

**它的理由不是"ffmpeg 更快"**：同一段内容转码之后 vp9/h264 上是 0.96×/0.99× 的打平；
早先"vp9 上 0.84× 不划算"是拿三个不同的视频比出来的（跨文件比连大小关系都会反），
"20 分钟窗口上慢 6–11%"是没交替跑造成的。性能不是这一条的论据（owner）。

**旧默认 `cv2` 留着**（`--decoder cv2`），给 A/B 和回退用。
详见 hw-decode-results 报告。

**`--prefix-min` 要单独说一句**：它是**堵一个没发作过的洞**，不是已兑现的改善——
产物几乎不变（三段切片里只有 hsr-s2 多出 3 条 run，主轨逐条同文本）。
留它的理由是 owner 的原则**少做特判**：无条件的 0.95 覆盖本身就是个特判。

### 1.3 `--reuse-v2` + `--refine-fused`（2026-09-17）—— **owner 决定，没走五部头对头**

| | |
| --- | --- |
| 改什么 | ①复用判据换成第二版（按手里文本的类别分门、框宽门、链首跨空档、回补；`--reuse-corr` / `--refresh-every` 的默认跟着变成 0.8 / 32）；②OCR 那遍同一次解码分出一路 540p 灰度全帧率辅助流，链首 / 文本变 / 链断时在线量回抠的像素信号，写进 obs 行的 `edge`；建轨结算回抠（[1.29](#129-建轨顺带结算回抠build_tracks---refine-auto2026-09-25-owner-定)）只读这些证据、不开视频 |
| 质量 | 复用判据：quick 六段 + 六段没见过的素材（70 min）实跑，**"高置信长文本的严重不一致" 0**、rec 调用 −32%（reuse-budget 计划）。⚠ 这把尺**筛掉的比留下的多**（低 conf / 相似 / 短句都不进这一栏）：同一批产物按管线自己的 conf ≥ 0.5 重数是 v2 18 条 / 旧判据 13 条，增量都是名牌 · HUD 的低分乱码（口径和数字在 reuse-budget 计划的警告框）。**它不证明漏条 / 误并 / 幽灵事件为零**，那要事件级留出集。在线回抠：开不开观测**逐行相同**（只多 `edge` 字段，2026-09-17 在 tmp/ab/fused 的两段上逐行核过）；四个逐帧真值段上首字 / 全字分档和两遍回抠**在噪声量级内不差**（每段真值 15–20 条，差 1–3 条读不出方向；那张表的产物是脏树产的，见 reuse-budget 计划的警告框）；字幕区 96–99% 的 run 拿到段首证据 |
| 收益 | 回抠每 5 分钟 35–105 s → 0.5–0.7 s，60 分钟窗口 2 s、不随片长涨；到帧精度的总速度约翻倍（约 3.5–5× → 7.5–12× 视频）。⚠ 这是对**两遍 auto**（全分辨率每帧）说的；和**快档两遍**（`--scale 0.5 --step 2`）比只快 14%–22%，长片上大致打平——进默认的理由更多在结构（不再单独开视频、窗按链开、不随片长涨），见 reuse-budget 计划末尾 |
| 代价 | OCR 那遍多付约 **+30%**（5 分钟片段上的读数；`wall_sec` 含每个 worker 5.4 s 的模型加载，**扣掉之后稳态是 +40%~+45%**，长片按这个读）。去哪了：主循环等帧——一个 ffmpeg 全帧率分两路出，采样帧的交付被拖慢。快档（辅助流隔帧：当时写 `--refine-step 2`，旋钮已删，现在是 `--aux-max-fps 30`）约 +16%；**09-17 晚复核过（修完网格对齐、两臂只差这一个旋钮）**：辅助流帧数减半、工作线程进程 CPU −5%~−38%，真值上**差别在 ±2 条以内、方向不一致**（原来那句「首字掉 2–4 条」没复现）——**仍不进默认**，辅助流的 CPU 不在关键路径上（reuse-budget 计划）。`--reuse-v2` 自己在新默认下只省约 5% 墙钟，它的主要价值是给在线回抠提供链事件 |

### 1.7 `--frame-select pts`（2026-09-20，owner："pts 更正确就按 pts"）

采样格从"按交付顺序数"（`select='not(mod(n,stride))'`）改成"按帧自己的时刻数"
（`round(t*src_fps)`）。**无缺口素材上两者逐字节相同**，所以只动 f3/f4 这类有丢帧缺口的素材。

两条依据：

* **解码器少交付时 `index` 会让整条格子静默平移**（NVDEC 在有前摇的 av1 上少 1~3 帧），
  `pts` 只是某一格取不到——失效形态从"全错且无声"变成"缺一格且当场喊"；
* **素材自己有缺口时 `index` 的相位被 `缺口 %% stride` 永久顶偏**，`pts` 始终锚在绝对时间格上。

配套改了三处（都是翻的时候踩出来的，hw-decode-results 报告）：
窗口**按 pts 收口**（`-frames:v` 是按数量收的，缺口处会越过 `--end` 约 5.2 s）、
`frame` 字段认 pts 而**内部 `idx` 留在交付序号空间**（辅助流的帧环按后者编号，混用会死锁）、
`frame` 的判据收进 `framesource.pts_frame` 一份（**写 obs 的地方有两处**）。

f3/f4 的用途 2 验收 **owner 定不做**（「属实没必要」）。回退 `--frame-select index`。
⚠ **帧号按名义帧率算**（2026-09-20，Codex 复审第三轮，hw-decode-results）：`round(t × 平均帧率)`
在有缺口的文件上会让相邻两帧撞号（f3 约每 46 s 一次），ffmpeg 路径因此改用容器的 `r_frame_rate`；
`config` 多一个 `frame_id: nominal`，**之前的 ffmpeg obs 一律不复用**、用到时按需重建。
⚠ **默认跟着解码器走**：ffmpeg → `pts`，`--decoder cv2` → `index`（cv2 本来就是自己按帧号数的；显式给 `--decoder cv2 --frame-select pts` 会报错）。

### 1.8 `--hwaccel cuda`（2026-09-20，owner 定：**理由是 CPU，不是墙钟**）

**墙钟收益很小，CPU 收益很大**——owner 据此拍板翻默认。同一段 wuwa-s2 5 分钟，
`typeperf` 整机 `% Processor Time` 每秒一采、减掉空闲基线、乘 16 核：

| 臂 | CPU 均值 | 峰值 | 墙钟 | **CPU 秒** |
| --- | ---: | ---: | ---: | ---: |
| 软解 | 47.3% | 68.3% | 42.3 s | **319** |
| **硬解** | **31.9%** | **45.8%** | 40.6 s | **189（−41%）** |

墙钟那一侧是交错三轮拉丁方量的：**−3.2% / −4.6%，落在噪声档**。
跑 flowocr 的机器往往同时是日常用机，**CPU 让出来比那 4% 值钱**。

**产物：文本和框不变，回抠证据变**。交错 A/B 上 21,587 行观测文本改 0、跨 conf 门 0、框一个不差、主轨逐字节相同；
但 **`edge` 的数值不同**——我原来写"回抠证据也一样"，只比了**条数**（`edge.on 481/481`），没比数值。
Codex 复审（2026-09-20 第二轮）指出后逐字段比了：wuwa-s2 30 s 上带 `edge` 的 320 行只有 **128 行**逐字段相同，
多数差 1 帧、**12 处差 10 帧以上**（`scale_cuda` 和 swscale 是两套缩放器；试过 `interp_algo=bicubic` 对齐，**更糟**，93 行）。
拿三段打字机真值判（对齐修好之后，hw-decode-results）：**软硬解差 ±1~2 条、方向互有，在噪声里**。
所以 `hwaccel` **不在** `SCHEDULING`（当天放进去过、又拿出来了）：软硬解的 obs 互不复用，用到时按需重建。

**能翻是因为先修好了两件事**（缺一件都不能翻）：

1. **`--frame-select pts`**（[§1.7](#17---frame-select-pts2026-09-20ownerpts-更正确就按-pts)）——否则 NVDEC 少交付 1~3 帧会让整条采样格静默平移；
2. **辅助流跟着硬解一起走**（`scale_cuda` 在显存里缩到 540p 再下传）——
   否则开硬解就自动退回两遍回抠（35–105 s），**开了净亏**。

⚠ **有些素材硬解交付不齐，自动退回软解**：NVDEC 在**有前摇的 av1**（首包 pts 为负）上少交付 1~3 帧，
`gi-s2` 连 pts 0.000 都不交付、`pts` 选帧也选不出第 0 格。照 `--workers` 的老规矩——
`framesource.hwaccel_blocker` 跑之前试解 4 格，不过就退回软解、把原因打出来、
`_meta.hwaccel_effective` 记生效值（`--workers N` 时各段合并，不一致写 `mixed:…`）。实测 gi-s2 退回、gi-s1 / wuwa-s2 正常开。
回退：`--hwaccel ''`。**默认跟着解码器走**：ffmpeg → `cuda`、`--decoder cv2` → 空（两个显式冲突地同给会报错）。

⚠ **纠正我自己一个估算**：我原来按"CPU 辅助流 9.08 s、GPU 缩完压到 2 s"估端到端 −21%。
**前半句对了后半句错了**：GPU 缩完实测仍要 1.89 s——**辅助流的开销不在缩放，
在把 3600 帧 540p 灰度（约 1.9 GB）搬过 PCIe 和 TCP**，`scale_cuda` 省不到这一块。
真要压它，旋钮是 `--refine-scale` / `--aux-max-fps`（扫描见 hw-decode-results）。

### 1.18 解码分片：`--decode-shards 2`（2026-09-24；decode-buffer）

现象（实测）：det / rec 一忙，一路硬解就慢 2 倍（只解码 12.1 -> 26.4 s），而解码单元本身远没用满；几路 ffmpeg 并行解就把它拿回来（只解码 3 路 −55%）。
病因是**推测**：硬解之后每帧（60 fps 的辅助流）都要 ffmpeg 自己的 CUDA 上下文跑一次 `scale_cuda`，而 Windows 上不同进程的 CUDA 上下文分时，
det / rec 一忙每一次都排队——按上下文的 GPU 时间线没量过（decode-buffer）。做法：3 路 ffmpeg 各排各的队：
窗口按关键帧切成约 20 s 的块、每块一个 ffmpeg（`-ss 关键帧 -noaccurate_seek`，按帧号区间取帧）、谁空谁领、按帧号顺序边解边交，
跑在只解码的子进程里；辅助流按块序转给回抠进程（它那边一行不改）。

**产物逐字节相同**（键在 `SCHEDULING`，翻默认**不让磁盘上的 obs 重建**）：分片对一路 ffmpeg，采样帧 / 辅助帧逐字节相同（gi-s1、有前摇的 gi-s2、yuka vp9）；
管线确定性路径 `obs_identical`：gi-s1 60 s、**wuwa-s2 10 分钟**（20,679 行）、**f3 跨丢帧缺口的 2 分钟**（10 s / 20 s 两种块长）、
**缺口落在第一块的 f3 1 分钟**、**f4 缺口两侧两段（缺口在中间块 / 第一块）**全部逐字节相同（最后这条是自检补的：第一块原来不带帧号区间，缺口在第一块时辅助流越界、回抠证据丢掉，已修，decode-buffer）；
默认路径打字机真值三段逐项相同；硬解中途出错整段改软解那条路（`hw_retry_check.py --extra "--decode-shards 3"`）Job / psutil 两条都过；改 2 路后 f4 缺口在第一块、gi-s2 文件头前摇两段仍逐字节相同；`hw_retry_check.py` 在新默认（2 路 + 预热）上 Job / psutil 两条都再跑过。

quick 六段交错两轮（`tmp/ab/q6shard`，3 路）：gi-s1 −3.1%、gi-s2 −9.0%、hsr-s2 −3.9%、wuwa-s2 +1.6%、yuka-f1 −10.6%、yuka-f5 −7.0%，**合计 −4.9%**；
加了字节预算之后另一个时间点复测（`tmp/ab/audit4`）：不分片慢 4.0%、**2 路比 3 路 −1.4%**（噪声档）——3 路每段都顶在 1 GB 预算上、第三路常年被挡着，所以**默认取 2**（少一个 CUDA 上下文、预取峰值约 0.6~0.8 GB）；
CPU 29% -> 37%，整机显存峰值 +0.3~0.6 GB（owner：内存增加可接受）。内存：没有消费者在等的块（纯预取）按**字节**封顶 1 GB（`decode_shards.BUDGET_MB`），
上限约是预算 + 消费者等待时顺带解出来的那几帧——块数有界不等于内存有界（长 GOP 切出长块、4K 上 20 s 就是 2 GB，2026-09-24 Codex 审计），
实测 1 分钟 f3 窗峰值 800 MB、2 分钟 f4 窗顶在 1,024 MB。关键帧**边探边切**（整片 f4 探完要 41 s，起流不等它）；
整块没交 / 块尾缺格按「源里有没有」判：有 = 解码出错（硬解那路整段改软解），没有 = 素材缺口（decode-buffer）。
供帧受限的素材收益大；UI 密、卡在 rec 的素材（wuwa）持平——解码一快，多出来的 ffmpeg 上下文反过来分时拖慢 rec，那一侧是下一个瓶颈。
撞上 `--decoder cv2` / `--frame-select index` / `--workers > 1` / 回抠开着却没 `--edge-proc` 时**安静让路**
（打印一行、`_meta.proc_split.decode_off` 记原因）；没 GPU（硬解开不了）时走一路软解、不分片（owner：每个操作要有能跑的 CPU 版，不求调度一样）。
混一路 CPU 软解进分片（原 `--decode-cpu-lanes`）2026-09-24 删掉（owner 定）：主要理由是那几块的辅助流像素随调度变（产物不可复现）；速度上管线里只在 gi-s1 上量过一次（整块缓冲那一版，2 硬 + 1 软比 2 硬慢约 1%），只解码的台子上它反而更快（decode-buffer）——"更慢"的证据很薄。
回退：`--decode-shards 0`。

### 1.23 采样和辅助流都按时间网格取帧：`--fps` / `--aux-max-fps 60`（2026-09-24 owner 要的功能）

**结论**：采样和辅助流都不再要求整除，按时间网格取帧，"采样帧 ⊆ 辅助流"嵌套（owner 定；高精帧环还没落地）。实现在 `flowocr.extract.framegrid`。

* **默认路径不变**：整除的情形（60 fps 素材上 2 fps 采样、辅助流 60 / 30）选帧表达式逐字相同、帧集合相同，
  obs 除 conf 末位外相同（GPU 上的 Paddle 本来就不逐次可复现）。**现有语料一份都不因此重建**（`out/` / `tmp/` 里的现成 obs 逐份查过：
  采样网格会变的只有 32 份更早口径的旧产物，它们本来就因配置对不上要重建）。效率噪声档（下面）。
* **不整除的辅助流量过真值**：精度由**最长间隔**定，不由平均帧率定——25 fps 不等距（最长 3 帧）和 20 fps 等距（也是 3 帧）同档，比 30（2 帧）粗。
  `--aux-max-fps` 不是严格上限：嵌套进来的采样帧会多送一点（60 fps 素材上限 25 + 采样 2 实际约 26 fps）。
* **不整除的采样只验证了功能**，质量没有公平的尺：打字机真值是按 fps 2 的采样相位抽的样（见下）。

怎么取：

* **时间网格**：帧率比 p/q（约分的整数）的网格，第 k 格是帧 `ceil(k·q/p)`，锚在帧号 0 上（帧号是 pts 帧号）。
  floor / ceil / 前后格都是整数闭式；p = 1 时逐项退化成原来"每 q 帧一帧"的整除算术。第 k 格离 k 个名义间隔不到一帧、不累积。
  ffmpeg 的 `select` 表达式和 Python 用同一组整数算，两边选出同一批帧（守卫在 6 小时帧号内抽查）。
  两个帧率之比离一个分母 ≤ 100 的简单分数不到 1e-5 就吸附上去：59.94 素材上给 `29.97` / `59.94`、23.976 上给 `23.976` 都是等距（审计抓到的，原来会被当成不整除）；
  59.94 上给 2 仍是真时间网格（离 1/30 差 1e-3）。
* **采样**：`--fps` 帧 / 秒。原来是 `stride = round(素材帧率 / fps)`，60 fps 上要 8 fps 实际给 7.5，59.94 上要 2 fps 实际给 1.998。
  不整除的要求**最长间隔严格小于 1.5 个名义间隔**（下游的容差——断链、并块——都是 1.5 个名义间隔）：60 上 40 fps 放行、45 fps 报错。
  按帧号 `n` 数的选法（`--decoder cv2` / `--frame-select index`）编不出不等距的网格，退回最近的整数步长并打印。
  窗口起点对齐到**帧距**最近的一格（`nearest`；不等距时不能按格号四舍五入，审计抓到的）。
* **辅助流**：帧率 = min(`--aux-max-fps`, 素材帧率) 的网格 ∪ 采样网格。上限是**上限**：不超过它 0.1% 就落得到整数步长时取那个步长
  （119.88 fps 的素材给 60 就是隔帧，不为多出的 0.1% 走不等距网格，Fable 复审）。回抠的边界锚在采样帧上，采样帧不在辅助流里边界就落不到它上面。
  并集退化成等距网格时证据记录照旧只写 `step`；不等距的写 `grid: [p, q, 采样 p, 采样 q]`，窗口两端对齐到网格、重建时按同一个网格数回来。
  回抠窗口里"上一个 / 下一个采样帧"一律问采样网格，不再按固定步长减。
* 约束：辅助流 ≥ 高精帧环（decode-buffer 目标设计里的帧环 S，**还没落地**）≥ 采样；现在只拦辅助流上限低于 `--fps` 的值。
  不等距的辅助流只配 `--frame-select pts` + 共享解码的辅路（nvdec / cuvid 那两路编不出绝对帧号），撞上就报错。
* 生效网格记 `_meta.sample_grid` / `_meta.aux_grid`（等距时 `_meta.stride` 照记）；复用判据比**生效网格**（按产物自己的 `src_fps` 算）。
  `--refine-step`（辅助流整除步长的下限）**删了**，被 `--aux-max-fps` 覆盖；旧产物记的步长折成网格照样比。
  只认等距采样的探针（`reuse_probe` / `skip_potential` / `probe_aux_reuse` / `probe_fps_gap`）遇到不等距的 obs 明说原因退出（`framegrid.meta_stride`）。

改动顺带修掉的两处"按恰好一个名义间隔比"的判据（等距整数帧率时结果不变，默认那臂打字机真值逐项相同）：
①`refine_from_obs` 认领"起点前一票"的段首证据改成 1.5 个间隔内找（原来要求恰好 `t_start − frame_us`：不等距时差 12 ms 就整条没认领上，
59.94 素材上 pts 取整也会差 1 µs）；②首字吸附到证据网格之后仍不晚于 `t_start`（网格是锚点折算的估计，毫秒时间基的锚点带 ±0.5 ms 舍入，
越过 `t_start` 时产物校验拒收）。同一族还剩的（融合的首字下界、断链容差仍按名义间隔）记在 next-steps。

### 1.24 det 换 ONNX Runtime、并进 rec 服务：`--det-engine ort`（D1，2026-09-24 owner 定；decode-buffer）

墙钟四个时间点 −1.7%~−3.2%，显存 +0.1~0.8 GB。改框（坐标抖几个像素）——回抠三处脆点修完之后，quick 六段 A/B 各两遍：

* **只对这一对成立**（2026-09-24 Codex 审计 P1 后收窄）：换了 `--det-model` 时 `--det-engine` 默认退回 paddle——内置 ONNX 只有默认那份的权重，

* 换了 `--det-model` 但自带 `--det-onnx`（这份模型自己的权重）时照样默认 ort，不静默丢掉给的 ONNX（Fable 复审）。
* **ORT det 不再借 Paddle**（2026-09-25）：前后处理配置从 ONNX 仓库自带的 `inference.yml` 读、DB 后处理是照抄 PaddleX 的一份
  （`flowocr.extract.detpost`，守卫对着 PaddleX 原实现随机对拍 + 真帧 120 帧 1,612 框逐字节相同）。于是默认路径（det / rec 都 ORT）的管线进程
  **一个 Paddle 模块都不 import**：起动的建模型段 4.7 s → 1.7 s（三段时间线各一次，`tmp/tl/base0925` 对 `tmp/tl/nopaddle0925`），

  没有 Paddle 的机器（`[cpu]` 装不上 paddle 时、非 Windows）这条路照样能起（`pyclipper` / `pyyaml` 是主依赖）。当时 `--det-engine paddle` 仍从 Paddle 的 predictor 取同一组参数。
  yml 的读法照 PaddleX `_build`（它不看的键这里也不看；守卫对着 `_build` 对拍七种写法）。**自带的 det ONNX 要连同它的 `inference.yml` 放在同一目录**，

### 1.27 ORT 线程池不自旋：`--ort-spin off`（2026-09-25 owner 定，GPU / CPU 一样；perf-nightly-0925 报告）

ORT 每个 session 一池 intra-op 线程，轮空时默认自旋一阵再睡（`session.intra_op.allow_spinning`）。管线给服务 `--spin 0`，两条路都关：

* **CPU 路径**：det 和 rec 的 session 各自吃满物理核，自旋只是互相抢——gi-s1 前 60 s `--device cpu`（rec 已按 [§1.17](#117-rec-池同时两个在途--rec-inflight-22026-09-23decode-buffer) 只留 1 个在途）64.1 → **51.3 s（−20%）**，
  主线程"提交"段 16 → 11 s、det 推理 49 → 38 s。
* **GPU 路径**：线程池大半在等 CUDA，自旋是空转。quick 六段交错两轮（`tmp/ab/spincpu`，整棵进程树的 CPU 由 `dev_tools/jobcpu.py` 记）：
  墙钟 −0.3%（噪声档；上一批 `tmp/ab/spin` −0.6%）、**CPU −8.2%（12 轮逐轮同向）**、文本改 0.043%（ORT 抖动那一档）。
  墙钟没提升，翻它凭的是省 CPU、规则从"按设备分叉"变成一条（owner 09-20：资源占用也是收益）。
  之前三段各一次的 −3%~−5% 是不同时间点顺序跑出来的，交错就没了——**又一次"单次读数 5% 档要换时间点复现"**。

同模型同输入、不改读数（NOISE_EQUIV），服务实际收到的参数记 `_meta.ort_server_args`；`--ort-spin on` 回退。
CPU 上两条调度规则（[§1.17](#117-rec-池同时两个在途--rec-inflight-22026-09-23decode-buffer) 末尾的 1 个在途 + 这里的不自旋）叠起来、不带任何参数的 `--device cpu` 端到端：gi-s1 前 60 s **72.2 → 47.6 s（−34%）**（`tmp/tl/cpu0925/base2`）。

**CPU 上不按形状分 session、不预热**（同日；`run_ocr2.ort_server_args` 在 CPU 上给 `--per-shape 0`、不给 `--warm`）：
按形状分 session 是 CUDA EP 每换形状就重规划的对策（[已知的坑](../dev-guide/pitfalls.md#ort-的动态形状)），CPU EP 没有这个坑，23 个预热 session 只是白建（每个一池线程 + 一份权重）。
gi-s1 60 s `--device cpu`：分 session 47.6 / 48.0 s → 单 session **43.5 / 44.0 s（−8%~−9%，两个时间点）**；全软解（`--hwaccel ''`，CPU 机器的形态）48.5 → 44.4 s，
解码在 CPU 路径上不是瓶颈（藏在推理下面）。和上面两条叠起来 72.2 → 43.5 s。同模型同输入、不改读数。
服务端另有 `--threads`（每 session 的 intra-op 线程数），管线里经 `--ort-server-extra` 透传（进 config）才用得上；
CPU 上按线程配额分核 2026-09-25 量过：每 session 6 线程墙钟 +7.7% / CPU −14.5%，4 线程 +25% / −31%，文本不变——只是拿墙钟换 CPU，默认不动（followups-evidence-0925 报告）。

### 1.28 det 批的流水：`--det-lookahead 1`（2026-09-25；perf-nightly-0925 报告）

gi-s1 上 det 线程忙 16.5 s / 主循环 18.1 s、主线程 21% 在等 det。现在下一批的前处理 + 推理在辅助线程上跑、和这一批的后处理重叠。

| | |
| --- | --- |
| 等价性 | 批的顺序、每批的算式都不变。Paddle 确定性路径（det / rec 都 paddle、`--rec-window 0`——异步池按"有多少取多少"拼批会让 Paddle rec 的 conf 随批组合抖，那 100 行差不是它）上 0 / 1 两趟 obs **逐字节相同**（gi-s1 60 s，2,257 行） |
| 单次读数 | gi-s1 主循环 18.4 → 17.6 s、主线程等 det 3.7 → 0.3 s（现在 56% 在等 rec）；wuwa-s2 22.3 → 21.5 s；yuka-f1 打平（det 线程 9.6 s 在等帧，vp9 的 NVDEC 供帧才是它的上限） |
| 交错 A/B | quick 六段两轮（`tmp/ab/look`，臂 `--det-lookahead 0` → 默认）：关掉它 gi-s1 +1.2%、gi-s2 +3.3%、hsr-s2 +0.5%、wuwa-s2 +1.8%、yuka-f1 −2.5%、yuka-f5 +0.7%，六段中位之和 +0.8%——**噪声档**（单次读数的 −4% 没复现）。观测 39,507 行两臂 (帧, 框) 全配上 |
| 为什么仍开 | **owner 2026-09-25 定开**。墙钟在这台机上被 rec 挡着、看不出来，但结构上它把 det 从关键路径上拿掉了（主线程等 det 3.7 → 0.3 s）、产物按构造相同；"弱卡上 det 是关键路径、这时有收益"是推测，没量 |
| 代价 | 多一个线程、多一批在途；解码头比 det 线程再多领先一批：帧环容量 +det_batch 个采样间隔（`ring_in_flight`）；共享内存槽不受影响（管线进程收到帧就拷走、放槽）。开着时 `stage_sec.det` 只含"等辅助线程的推理 + 后处理"，和关着的不能直接比 |
| 守卫 | 假检测器上 0 / 1 同序同值（含尾批）、推理出错两档交出同样多帧再抛同一个错、提前关不卡；`--det-lookahead` 只收 0 / 1 |

回退 `--det-lookahead 0`。

### 1.31 匹配器的相邻合并按区域判（2026-09-26）

`scriptmatch` 把"相邻两条 cue 认的是同一条剧本行、间隔 ≤ `--merge-gap`（2 s）"并成一条；"相邻"原来按喂入序列判。
默认的 `--feed nonoise` 把各区域的 cue 按时间交错着喂，同一句话被一闪而过的杂项（`0`、`D`、按键提示）切成两条时，中间常夹着别的区域的 cue，
于是并不上、换成原文就是同一句打两遍——gi2 整场的重复认领 165 次里 122 次是这种间隔 ≤ 2 s 的。现在按**来源区域**各自判相邻；
只并同一区域的，主对话和阅读面板里的同一句不会并成一个叠加块。`--feed main` 只有一个来源，行为不变。没有开关（改的是判据本身的"相邻"）。

### 1.32 回抠结算救回被回补作废的结尾证据：`--refine-salvage-end`（2026-09-26）

在线回抠的结尾窗证据，所在那一段的历史文本被回补改写时整条作废（`stale`）。可结尾窗量的是**框里像素什么时候变**、模板是末次观测那一帧，
而结算按"末次观测时刻 + 框"把它认领到 run 上——这两样回补不改。所以窗口凑齐了的（不 `short`）照样用，只去掉作废标；窗口不全的仍不用。

### 4.1 主轨的接受判据**把画面上部的正文排除在外**（有意的取舍，audit-5）

`pick_main` 只接受 `label_region` 给出的正文类标签，而那两个标签本身带 y 约束：
`subtitle` 要 `cy > 0.60`、`dialogue-or-caption` 要 `0.35 < cy ≤ 0.95`。
**所以字幕长在画面上部的素材会得到"没有主轨"，而不是挑错一条。**

这是**有意的**：zzz-s2 那次挑错（挑中屏幕顶部的人名带）正是靠这条修好的，
九段切片上改判据后 9/9 挑对（gamestream-first-look 报告）。
代价写在这里，免得下次遇到顶部字幕的素材再从头查一遍：
**没有主轨 ≠ 没找到文字**，逐区域产物照常在。

## 5. 一条贯穿全局的教训

2026-09-08 一天之内，**四次**"一个小扰动就把主轨换到别的区域"：

| 改动 | 幅度 | 后果 |
| --- | --- | --- |
| `--slot-span-ratio 2.0` | 一个阈值 | 9 段切片里 3 段换区域 |
| `--slot-geom median` | 签名算法 | f1 的 191 条连续台词跑到 region07 |
| `--gap-frames 2` | 容差 +1 帧 | wuwa-s1 换区域。**09-14 用文本库重量**（try-list-results 报告 M1）：gi-s2 / hsr-s2 命中 +0、cue 与重复认领都降；**gi-s1 主轨换到 cy 0.50 的 region04，命中 30 → 0**（台词还在 region00 的逐区域产物里）——这次符号是负的 |
| `--rec-batch-size 8` | **OCR 文本变 4%** | f4 换区域，**−662 条命中** |

共同病根是**主轨 = 按分数挑出来的单个区域**。所以：

> **任何改动都可能通过"重新洗一遍聚类"影响用途 2 的命中，
> 而这和改动本身好不好没关系。** 报一个改动的端到端效果之前，
> 先看主轨是不是同一个区域（`provenance.main_srt`）。

`--main-band` 缓解了它，但**只是绕过 `stitch_slots` 的缺陷，不是修它**——
那一层仍有两条独立证据：判据拦不住不该进来的、进来之后签名漂了（整片 44–45%）。
