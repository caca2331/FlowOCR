# 验证与报数

改完怎么验、报数怎么报。每一条都是踩过之后定的，出处写在条目里；和具体代码、数据相关的坑在 [已知的坑](pitfalls.md)。

## 先定指标，再看结果

任何"效果更好"的说法都要落到事先定义的指标上，不接受看完结果再定标准。基本指标（2026-09-03 第二轮验证时定的）：
轨道召回 / 误报、时间边界误差、文本 CER。用途 2 把准确性重心挪到了**漏条 / 幽灵条目 / 切分口径 / 时间精度**上（产品方向记录），
所以有原文剧本的素材上，主尺是疑似漏字幕判断器的输出覆盖（有内容档）加重复认领：`gametext` 素材和《魔裁》的臂间比较都是（下面「报数口径」）；命中与漏条降为诊断尺，对望言基线的头对头仍用命中三档。

**先怀疑评测口径，再怀疑算法。** `compare_timing` 上栽过三次：
①按时间重叠配对时，一条 100 秒的常驻条目抢走 3 秒参考条目的配对，误差看着从 1.0 s 恶化到 19.5 s；
②改成按文本配对后，VideoSubFinder 的时间轴正文写的是时长不是台词，10 条参考配上 0 条，脚本只打一行汇总、退出码 0；
③误差只在"配上的条目"上算，回抠前后配上 6 条 / 5 条，两行中位数根本不是同一批。
现在 `--match auto`（认出无文本参照就退回 overlap 并明说）、配上 0 条非零退出、汇总永远打印"配上/总数"、样本 <20 不报 P90。
**A/B 必须 `--pair-report` + `--common-with` 取交集。**

**离线重放一条策略时，只给它实现看得见的东西。** 复用判据当初靠离线模拟定（`--no-reuse` 的 obs 当真值，按 IoU ≥ 0.7 把相邻采样点的框连成框链，在链上逐帧跑策略；像素信号和策略无关，可以重放、不用重跑 GPU），第一版两次把结论带偏（reuse-budget 计划）：
- **发现变化只能靠端点。** 真实管线只在真读了的那一帧知道文本，中间沿用的帧读数是抄来的；拿真值去扫窗口中间找变化点等于开天眼，报出来的"−34% / 换字 0"全是虚的。
- **触发用原始文本不等，不用"严格内容变化"。** 实现分不出这次不同是抖动还是真变了；损害照严格判据数，那是评价口径，不是实现看得见的东西。

配对表（"这一对放行对不对"）也替不了端到端模拟：错误会串、产物是 run 不是帧、可以回头补、成本按框宽算。

## 跑多长：按证据强度分档（owner 2026-09-08）

| 改动的性质 | 跑多长（素材总时长） |
| --- | --- |
| 一般性改动 | **≤ 30 分钟**，选几个代表性片段（`sampleset.sh quick`） |
| 需要大量证据 / 阶段性结论 | **120–240 分钟**（`sampleset.sh evidence`） |
| 确实非必要不可 | 再往上，**先说清为什么** |

- 代表性片段的清单在 `data/samples.md` / `data/samples.json`（本地，不进版本库；按素材、画面类型、已知病灶、有没有剧本分类）。
  样本集：quick（30 分钟，一般性改动）/ evidence（约 150 分钟）/ holdout2（ui-gate 的留出集）/ zh（中文 + 非满屏 + 飘屏弹幕，2026-09-20 补，已经被用成开发集）。
- yuka 那几段不切文件，用 `run_ocr2 --start/--end`：时间戳仍按原片绝对时间写，窗口结果能直接和整片参照对齐，也不违反"素材只读"。
- 非必要不跑五部整片；不量效率的臂可以并行拉起来。
- **改提取层都要过打字机真值**（owner 2026-09-23）：边界时刻的错只有它量得出。`dev_tools/typewriter_eval.py`。
  打字机真值是按 fps 2 的采样相位抽的样（139 条全是 fps 2 采到打字中途的），**量不了采样网格**；和网格无关的那批（`data/gt/twfree-*.json`，`dev_tools/tw_sample.py` 抽）2026-10-05 只有 6 条，还不够判网格。
- **改聚类先跑聚类的尺**（`flowocr.analyze.slot_pairs`，cluster-ruler 计划）：误合并 / 误拆分分开量；
  每条臂在照自己抽的样本上都最差，比臂要两个抽样框合起来报。现有的 acceptance 文件已经被看过、也进了 learned 模型的训练，只当开发集用；
  真要翻聚类默认时另抽一批新的（照默认臂和候选臂各抽一框、取这批素材以外的片段，约 80–160 对），新的那批只看一次（owner 2026-10-06）。
  `lines` / `learned` 两条臂量的是 `build_tracks --cluster` 的最终分组（和管线调同一个函数）；
  S5 层（同时在场、上下相邻的两行，不照任何臂抽）量"一个框里的几行是不是一条轨"，各臂在它上面是同一个率，单独报、不并进 S2–S4。
  - **尺的标签噪音**：2026-09-24 盲复标 50 对，一致 40 / 50（80%，Wilson 95% 约 67%–89%），16% 的对计分身份变了（进出 same / different）。复标者和原裁决者同一家族，所以这是噪音的**下界**。
    噪音只经过**两臂判法不同的对**改排名（两臂同判的对上的错两臂同额，只改绝对率）：比臂读分歧对上的比分，"好约几个点"这种量级在标签独立复标之前不稳。
  - **标注协议**：单位是 run 对，标注时不看各臂判法；四类 same / widget / different / unsure，先给两框各自分类、类别不同直接 different。易错三条：双语字幕与游戏字幕是 different；OCR 读出的纹理是 unsure，不是 different；同一块评论墙里隔得远的两行是 same。
  - **摆帧画框用 `slot_pairs.box_at(r, t)`**，不用 `r.box`：动过的 run（滚动面板、评论墙）的 `r.box` 是最后的位置，画在中途帧上会框到另一行（2026-09-24 查出 920 对里 97 对画错行）。
  - **真值的 run 对不回当前层时各臂都不计这一对**，并打印丢了几对；`dict.get() == dict.get()` 会把两端都丢的算成同类。
    尺的真值绑定到 run（起止时刻、框、文本）：同一份 obs 上直接用；跨 obs 版本先重新锚定（`slot_pairs.reanchor`），只报对得上的子集和丢失数，不据此宣称完整样本无回归（project-structure 计划）。
  - **聚类旋钮的读数看逐对翻转清单**（`dev_tools/h_ratio_ruler.py` 打的），不只看总数：放宽不单调，去掉一道门时"该合"的对里也会有对变成分——缝合是贪心、签名驱动的，窗内多并一点，后面的分配整个重洗（h-ratio 计划）。
- **改 ASS 的时间 / 效果标签（`\t`、`\fad` / `\fade`、`\move`）或把一条事件切成几段，以 libass 逐帧对照为准**（`dev_tools/ass_framediff.py`）：
  拿改之前的写法或不切的一整条当参照，渲出来要逐帧相同，差异帧只许贴在事件端点上（采样时刻正好落在端点时两种写法可以合法地差一帧）。
  守卫里断言标签字符串的只钉写法：09-26（预览切段后淡入从全透明重来）和 09-27（阶段 4 分段后 `\t` 的结束时刻减成 0，libass 读成到段尾）两次都是字符串守卫全过、画面是错的。
  `--selftest` 用这两种形状自检（修之前的写法报差异、现在的写法逐帧相同）。
- **改 `build_tracks` 先跑 `track_health`**（条/h、cue 时长中位、逐字重复率、常驻短行占比，只看产物自己）。
  下游指标不会告诉你产物坏了：input4 的主轨 20,108 条里 64% 是逐字重复，头对头的召回分反而更高（碎片化给了匹配器更多机会）。

### 小样本上的结论不外推

- 60 秒片段上的结论不能外推到长片：空间聚类就是这么翻车的（clustering 报告）。任何新判据都要在整片上再验一次。
- 40 分钟窗也不行：yuka 的 40 min 窗上字幕带还是干净区域，6.2 h 整片上它被串进巨型区域、缩窗无效。
- 短窗口上"主轨 = 单个区域"本来就不稳：small_det 在 5 分钟最密窗口上"把主轨跑碎"（83→110 条），两个 20 分钟窗口上没复现，f5 上反而是 medium 更碎（2026-09-10）。
- **报窗口数据必须连「整片还没验」一起报。**

## A/B 的规矩

- **两臂必须是同一段素材**。跨素材比出来的倍数连大小关系都会反（2026-09-10：解码三条路原来拿三个不同视频比，得出"vp9 上 ffmpeg 0.84× 不划算"，同内容转三种编码再比是 0.96× / 0.99× 打平）。
  同一个文件里"跑哪一段"的方差比"跑多长"大十倍，所以探针一律要有 `--start`，报数时段落要和素材名对上。详见 hw-decode-results 报告。
- **两臂的固定开销要么都算、要么都不算**（`cv2` 的容器打开 vs ffmpeg 的进程启动），比值按扣掉启动的稳态读。拆进程的数要把起动和稳态分开读（端到端 − `wall_sec` = 起动）。
- **对照臂把关掉的旋钮显式写出来**：默认值一翻，"空参数 = 旧默认"就塌成同一条臂。驱动跑之前过 `dev_tools/arm_check.py`（比**解析后的生效配置**，不比参数字面），撞了就停。
  回抠同理：建轨默认按 obs 里的在线证据结算（`--refine auto`），对照臂是 `--refine off`；要拿开视频离线测量核对在线证据，
  用 `dev_tools/refine_offline_probe.py`（输入是 `--refine off` 的产物，显式 `--decoder cv2` / `ffmpeg`，不写产物）。
- 驱动开臂：`sampleset.sh` / `run_full_ocr.sh` 用 `OCR_ARGS` + `ARM`（给了 `OCR_ARGS` 不给 `ARM` 会被拦下，两臂写进同一个文件是静默错误）；`head2head.sh` / `gametext_eval.sh` 用 `SUFFIX` + `BUILD_ARGS`。
- **一次只改一条，一条一对账。"改完没变"是最便宜的证伪，先跑它再写结论。** 同一批里改两处只对一次账，写出来的"逐字节相同"就可能是错的。
- 报 A/B 的数只准写臂名，不写"默认 vs X"（[defaults.md](../architecture/defaults.md) [§0](../architecture/defaults.md#0-报-ab-的数只准写臂名不准写默认-vs-xaudit-5)）。
- 两份建轨产物对账用 `dev_tools/tracks_identical.py`（先剥 provenance；**先拿同一份代码跑两遍 A/A**，确认确定性再比 A/B）。
- 默认路径（异步 rec 池）不是逐次可复现的：批组合随机器忙闲变、conf 末位跟着抖，读数又是回来就结算，rec 的快慢会改哪些帧真读，所以同一配置两次之间文本和事件也会动（2026-10-11 quick 六段窗口 4：每段一侧独有事件 0~3 个；owner 定这种抖动不防）。`obs_identical` 验不了，用 `obs_textdiff` / `rec_engine_accept` 的分栏和 `arm_events`；A/A 底噪要实测，和 A/B 并排报。
- 短窗的 A/A 干净不等于长窗也干净：2026-10-01 GPU 默认路径的 120 分钟代表集（九个窗口）做新旧代码对照，七个窗口有少量文本或边缘证据变化；这七个窗口再跑同版本 A/A、B/B，同类变化照样出现（例如 yuka 一窗 A/A 三行文本、五行边缘证据，建轨事件差 1），七对同版本比较还合计出现 14 次 conf 跨 0.5 门（按跨门的观测行计）。不能把短窗的"只动 conf"当作通用保证；没有合格真值的窗口不计准确性通过。
- 要逐字节对账（"只改什么时候算"的改动、结构性重构），走**确定性路径**：`--device cpu --hwaccel= --rec-window 0`（纯软解、CPU 推理、同步窗口，`--workers 1` 是默认）。
  2026-10-02 在 gi-s2 0–60 s 和 yuka-f5 14840–14900 s 上同一份代码跑两遍都逐字节相同（除 `_meta`）。成立条件是同一台机器、同一份 ORT 构建、CPU 线程数不变；
  跨机器是否也逐字节相同没有依据。默认的异步 rec 池按"有多少取多少"拼批、读数回来就结算，conf 和读哪些帧都随机器忙闲变。先做 A/A 再比 A/B。
- 事件级对账用 `dev_tools/arm_events.py`（IoU≥0.7 + 时间重叠）。

- **新收益旋钮的对照臂要叠在已上线的收益之上**，只差这一个：攒批在没开预取的臂上 −4%~−13%，换到已带 `--det-prefetch 2` 的臂上是 +1.8%~+4.8% 或持平（2026-09-18）——不叠上去，就把预取的功劳算进了攒批（inference-runtime 计划）。

## 墙钟：按差幅分档读（owner 2026-09-05）

开发机同时是日常用机，GPU / CPU 会被别的负载占用，但噪声不是无结构的：

| 差幅 | 怎么读 |
| --- | --- |
| 明显的正向提升（远超 5%） | 显然有效 |
| ≈5% | 大概率是真提升，换个时间点再复现一遍 |
| < 5% | 可能是噪声，同样要换时间点复现 |
| 意外的大幅负向波动 | 说明机器上确实有别的负载，先怀疑这个，再怀疑代码退化 |

- 别把"机器可能不干净"当成放弃墙钟数的理由。5% 及以下要么等第二个时间点复现，要么改用**同一次运行内部的比例**（cProfile 占比、rec 调用数、复用率），后者对负载不敏感。
- 墙钟 A/B 用 `dev_tools/ocr_ab.sh`（同一段各臂紧挨着、逐对换先后），别拿两次驱动整批跑的结果相比。
- 交错跑也有盲区：ABBA 抵得掉线性漂移，抵不掉正好落在中间两次的负载（hsr-s2 读出 +15%，四对复测 −2.1%，2026-09-10）。读到意外的反向，先看逐次读数的时间顺序，再加对数。
- 墙钟和资源一起报（资源占用也算收益，见 [采纳规则](../architecture/defaults.md#采纳规则改动凭什么进默认)）：
  `ocr_ab.sh` 每次运行经 `dev_tools/jobcpu.py` 记**整棵进程树**（监督者、worker、ORT 服务、解码 / 回抠进程、ffmpeg，含跑完就退的）的
  CPU 秒和同一时刻的提交内存峰值，旁注 `<产物>.cpu.json`，报表自带 CPU 一栏。只看 worker 自己的进程时间会漏掉 ORT 服务这类大头。
  同一份旁注的 `res` 是按进程的资源画像（`dev_tools/resmon.py`，0.25 s 一拍）：私有工作集之和的峰值、各角色（ORT 服务 / 解码 / 回抠 / ffmpeg）的峰值、
  独占显存和**显存上界** `gpu_bound_mb`（非 ffmpeg 进程之和的峰值 + 同时在世的 ffmpeg 最大数 × 单个 ffmpeg 的显存——分片下每个 ffmpeg 只活 1–2 s，按拍采样会漏）。
  共享显存（`gpu_shared_peak_mb`）平时也不是 0（ffmpeg 下载帧要用），判"溢到系统内存"要和不压显存的那一趟比。
- 优化之前先 profile，别凭印象归因（见 [已知的坑](pitfalls.md#优化之前先-profile)）。
- 提取层的效率要算总账，把回抠那一遍算进去：两遍回抠在 av1 上曾是 OCR 那遍的 5–9 倍、换 ffmpeg 窗口解码后仍 1–2.6 倍，所以**省 rec 之前先看这一遍**。
  默认的两遍合一遍（`--refine-fused`）让回抠只剩每 5 分钟 0.5–0.7 s，代价是 OCR 那遍多付约 +30%；和快档两遍（`--scale 0.5 --step 2`）比只快 14%~22%（reuse-budget 计划）。

## 报数口径

- **写进文档的每个数，都要能从产物里数回来。** 口径定死：**一条 = 一个 SRT cue**；数 SRT 只用 `grep -c -- '-->'`
  （`^[0-9]*$` 会把空行分隔符也算进去、约等于真值的两倍；`^[0-9]\+$` 会误算正文是纯数字的条目）。
- **报一个"0"的时候，连它筛掉了多少一起报**；筛子的名字要写清它筛的是什么。复用判据的"换字 0"曾被写成"真错字幕 = 0"，
  那把尺要求 conf ≥ 0.9、内容 ≥ 3 字、非前缀、相似度 < 0.6，筛掉的比留下的多得多。现在叫"高置信长文本的严重不一致"，它证明不了漏条 / 误并 / 幽灵事件。
- **报一道门的分，要连门的全部参数一起写**：常驻 UI 门的留出集打分时漏传一个门参数，精确 / 召回读成 66.7% / 44.4%，实际是 75.0% / 83.3%，看着像判据退化。门的真值按框位标（该剔的 UI / HUD / 水印，不许剔的名牌 / 台词），先摆帧再标、标的时候不看判据输出；
  打分只读判据吐出的判决、不重写判据。一份留出集在判据照它的错改过之后，就不再是留出。
- **峰值不能跨 worker 相加**（三个 8 MB 上限被拼成 21 MB，看着像上限没守住）。
- **指标的门不能等于接受判据的门**：`scriptmatch` 的"可疑改写"取了 `--fuzzy`，结构上恒为 0；门必须高于 `--fuzzy`。
- **判据 A 救了判据 B 救不了的情形，就不能再拿 B 去审 A**（2026-09-16）：拿"认领的剧本行 vs 重叠 cue 的相似度"去审匹配器，和匹配判据是同一个函数，
  标出来的正是上下文加分按设计工作的地方。匹配命中里的错认，没有任何文本相似度做的尺量得出来，只能抽样摆帧。
- 字幕的读写与"条数"口径只走 `flowocr.artifacts.srtio`（`read_*` 会拿解析结果和 `count_cues()` 对账），评测工具的自检只走 `flowocr.artifacts.evalkit`。
  历史上 5 个工具各写各的，拼行分隔符有三种，代价是一个错了 30 小时的计数。

### 疑点工具与摆帧判读

- **疑点、清单类工具（只给线索、要人摆帧）的规则去留看独有命中**：别的规则不报的真错就留；精度只用来给人排先后、写进手册，不当去留门槛（owner 2026-10-07，推翻了先按精度删规则的做法；时间疑点计划）。
- **摆帧判"起止对不对"时，判据的容差要小于要量的差**：容差 0.5 s 时，离起止 0.2–0.3 s 的帧会把"提前 / 推迟 0.3 s"判成对，取帧要离起止 ≥ 0.6 s。
  改动本来就在容差之内（比如终点夹掉不到 0.5 s）时，"修错为零"必然成立、等于没测，要在新旧两个时刻之间摆帧，看新时刻是不是更接近字实际出现 / 消失的那一帧（时间疑点计划、检测器三场修复计划）。

### 有原文剧本时：三档、命中集合、重复认领

- **疑似真漏按内容字数分三档**（owner 2026-09-06）：纯标点 / trivial 1-2 字 / 有内容 ≥3 字。五部实测三档差两个数量级
  （97.6%–76.0% / 21.3%–8.1% / 0.5%–1.2%），混成一个"漏条率"必然把结论带反。`evalkit.triviality()` 是唯一口径，`script_align` / `h2h_report` 默认按三档印。
- **三档不能跨 A/B 臂比**：`gap_short_entries + gap_long_entries` 恒等于 `dialogue_entries − dialogue_hit`，漏条只是命中的镜像，周围条目一旦被匹配上，漏条会被重新分桶。
  `script_align` 的三档只在同一条臂内部说明结构；臂间报表用 `dev_tools/arm_table.py`。
- **跨臂比命中集合**（审计三）：命中是集合，集合差不经过 gap 分桶，按三档拆是合法的：`dev_tools/hit_delta.py`（默认按归一化文本的多重集求差）。
  第一次这么拆就把结论改了：并名牌的净命中 +27~+151 里，主体是纯标点档，"有内容 ≥3 字"在 f3/f4/f5 上是 −7/−15/−5（methodology-audit-3 报告）。
- **疑似漏字幕（不只字幕带台词）**：`dev_tools/miss_detect.py` 在 `gametext` 的匹配产物上，把圈中单元里该出现的行（台词、选项、过场字幕、黑屏旁白、界面文字，
  排掉没播 / 没走的分支 / 重演拷贝，变体并到代表行）逐条分进五类：已输出（按显示协议的默认可见规则画出来、有该语种文本）/ 另一版本已输出 /
  匹配器决定不显示（行的组默认不可见）/ 漏（读到过没输出，带定层：画不出来、认领了没生成条目、建轨没留下、没喂、认成别的行、没认上）/ 没读到；
  按组 × 三档出表，覆盖 = (已输出 + 另一版本) / (该出现 − 决定不显示)。"读到过"：有叠加条目、或认领它的记录的 OCR 原文（合并时取的最长那条 cue）里有一行非名牌的读数撑得住它的算（`名前：台詞` 先剥掉名字）；其余的行有没有 gamescript 锚点都要在它的时段里搜 obs
  （一帧里上下相邻的框拼起来比，读数要占这一行过半、且八成落在这一行里）；不到 3 个内容字的行不搜（三档的口径和搜读数的 `cnorm` 口径，哪个说短都算；宽时段里 `……` 处处都有），认领有读数撑着的算读到过，其余记"没读到·太短判不了"；整行是说话人名的不搜。
  只凭锚点不算：开头相同的另一句台词、打字机半截读数都能锚上来（摆帧 20 条"漏"里 8 条是这种）。
  定位到的字盖住这一行不到一半的，不按事件定层、记"定位弱"。
  另出 B 清单：没画成译文的事件里有 ≥3 个假名汉字、没被任何该出现行定位到的，按区域汇总。
  剧本 key 是主键，`--vs` 逐条比两臂（剧本 provenance 不同就拒），新漏 / 修好按定层拆，`--out` 两臂都写。它取代了只看字幕带台词、按认领判的旧工具 `missed_trace`：删之前四场整场逐 key 对照过，
  分类或定层不同的都落在三种已知成因里（检测器要 OBS 读数撑着、锚点不算；检测器自己在窗里搜 OBS；多出的定位弱一层）。
  `naninovel` 的匹配产物（顺序剧本，《魔裁》）也能量，要给 `--span-ref`（正文是剧本原文的参照字幕）：对上的剧本下标分段圈出区间（隔 200 行以上断开、不到 5 条的段当误对丢掉；`script_align --span-ref` 取最前到最后，一条误对就把没播的整章圈进来），区间里匹配器认得了的字幕带行是分母；没有锚点，时间窗由剧本顺序上前后已输出行夹出，输出变了窗也跟着变，读到过照样在窗里搜 obs；定层的喂入按主轨 cue。两个适配层搜读数时都排掉"逐字就是剧本里另一行或说话人名"的读数（法庭辩论屏上"反論"按钮的缩写能盖住一句台词的大半）。naninovel 上"另一版本"还要说话人相同（顺序剧本没有按主角分的版本，字相近、说话人不同的是另一个人的另一句）；gametext 不卡，绝区零两位主角各说一版的台词正是另一版本。区间里没播的分支也在分母里（顺序剧本没有处境），覆盖的绝对值偏低，比臂看差。《魔裁》的臂间比较：`head2head.sh` 每条臂多跑第 4 步（naninovel 匹配器 + 检测器；基线是随素材来的 ASS、过不了 naninovel，头对头照旧走 `match_ref`），`arm_table` 有这份产物时多印一张覆盖表，代价栏是重复认领里回显判定为"其他"的；检测结果记检测器和匹配器的代码指纹，两臂不同就逐行拒比。换喂法、并名牌的臂跳过这一步（naninovel 只喂主轨，量出来和同建轨的臂一样），`MISS=0` 整步跳过。**《魔裁》臂间的主尺也是这张表的覆盖加重复认领，主轨命中三档降为诊断尺**（owner 2026-10-07）：第 5 部按层抽帧量过漏报，有内容档按点估计约 4 条（上界约 175 条，几乎全来自没播的庭审分支），其余四部没量；对基线的头对头照旧是命中三档。
  **`gametext` 素材上用途 2 的主尺是它的覆盖（只数有内容 ≥3 字的行）加重复认领，主轨命中降为诊断尺**（owner 2026-10-07）。
  尺以漏报为主：检测器把真漏判成"没读到""另一版本已输出"，比多报几条危害大得多。四场整场按层抽帧量过，有内容档按点估计四场约 8 条真漏没报出来
  （抽样小，各层 95% 上界合计约 84 条）；
  纯标点、1–2 字档几乎全漏、检测器记"太短判不了"，按产品方向这两档不追。报的"漏"仍是线索、结论要摆帧，精确率照报、不设门。
  覆盖的绝对值主要被"没读到"拉低，而这些行摆帧看多半是没播的分支或另一版本：比臂看两臂之差，不拿绝对值比素材。
- **命中要有 OCR 文本支撑，填位另记一档**（2026-10-05）：在匹配器的输出上量命中时，文本已换成剧本原文，游标对齐必然逐字命中；
  而带上下文动量的匹配器会把剧本行填在没读到这句的 cue 上（yuka f5 发饰误读的 `大` / `米`）。所以一条剧本行要在认领它的输出 cue 时段里，
  喂给匹配器的那份 OCR 有一条读到了它（`script_align.supports`：共有内容字占这一行过半，或 ≥3 字且占那条 OCR 过半；1–2 字的行要字全在），
  才进命中；其余记「填位」。`hit_delta` 恒按这个口径（填位单列一栏），`script_align --fill-ocr` 在 JSON 里多给 `dialogue_hit_text` / `dialogue_fill`，
  `h2h_report` / `arm_table` 有这个字段就用它。不分开的话，往主轨里灌垃圾 cue 的改动在这把尺上显得有收益。
  内置 `gametext` 匹配器的认领本身就要求文本相似（≥ `--fuzzy`、整行包含或打字机半截），四场整场上逐场只有 0–2 行认领没有文本支撑，读数基本不变。
  在没参与调参的两条 yuka 臂上抽查（agent 判）："有支撑"60 条对 58 条，"填位"35 条对 31 条——错的填位都是 OCR 读到了但读错了字（`ふふん` → `不不ん`），判据偏严；纯标点行可能被长句里的省略号撑起。
- **主轨口径（`game_align`）的读数 2026-10-05 起变了**：它和 `gametext` 匹配器共用 `game_align.run`，那天加了"改认以它开头的更长台词"和"打字机半截"两条认领，
  四场整场同一份轨上主轨命中 +1 / +6 / +2 / 0、行尾缺字 +1 / +6 / +1 / +1。和那天之前记下的主轨读数比，要用同一份代码把两臂都重量；之后加的第四遍（读到一大段，10-10）、第五遍（夹缝认领，10-24）同理。
- **命中不许单看，代价用「重复认领」量**：输出里某条剧本行出现的次数比整部剧本里它的条数多出多少。不依赖游标 / 分桶 / 参照时间轴，能在匹配器输出上算。
  它是**报警，不是已确认的错误数**（真实重播也会让它涨，两臂各自下界之差不是错误增量的下界）。地板 1.4–2.8%，看臂间增量。
  `scriptmatch` 按**带内 / 带外**分开报（2026-10-06，产物 `stats.repeat_extra_band` / `repeat_groups_band`）：带外是文本包里的 UI 文案、散条目、选项，本来就反复上屏，**报警只看带内**。
  四场整场多出的 55 / 48 / 168 / 236 次里带外 1 / 38 / 39 / 198（gi1 / gi2 / hsr / zzz），zzz 混在一个数里会把台词的报警淹掉。
  带内再按回显判定拆成**重播 / 回显 / 其他**三栏（2026-10-06，产物 `stats.repeat_extra_band_echo`，回显 = `same_time` + `log`，判法见 [artifacts.md 的回显判定](../architecture/artifacts.md#1-一级产物只有一份)），
  **报警看"其他"**：重播是真实重演、回显是同一句出现在别处或对话记录里，都不是错。四场带内 54 / 10 / 129 / 38 次拆成重播 7 / 7 / 7 / 4、回显 21 / 1 / 94 / 30、其他 26 / 2 / 28 / 4。
  "其他"里有同一次显示被一闪而过的别的 cue 隔开、合并没并上的那一截（同区域、和主相接），它们不是错认但仍进报警。`naninovel` 的产物没有带内 / 带外之分，拆的是全部（`stats.repeat_extra_echo`）。
  **重复认领按代表行数**（2026-10-06 起，owner 定）：同一句的两种说法（变体组）各被认领一次也算重复，和覆盖同口径；那天之前的产物按原始 key 数（zzz 整场 228 → 236），跨这天比要用同一份代码把两臂都重算。
  `unmatched_subs`（"幽灵条目上限"）在匹配器输出上结构性恒为 0，量不了任何东西。
- **纯标点行不作强求**（owner 2026-09-17）：有原文时靠上下文 momentum（剧本顺序 + 名牌把短 cue 撑成有边界的条目）对齐；
  哪怕被当噪音丢掉、动量因此断了，代价也很小。别为保护它堆机制。
- **名牌别并进给匹配器的合并流**（审计三）：独立成条的名字 cue 会去抢剧本里含名字的行，净收益几乎全在纯标点档，每条覆盖重复认领涨 2.2–7.0 条。
  贴进正文首行（`merge_nameplate --paste`，贴法 99.8% 准）净贡献 ≈ 0。名牌信号留在逐区域产物里给用途 1。

- **命中集合的分辨力看样本大小**：quick 片段上有内容档只有几十条命中，只换一个不该影响产物的旋钮（`--workers`）就能让它 ±1，所以"全 0"只读成没看到反例，报数写明命中数和分母。
  比两臂的文本哪个更对，别靠读例子：抽样带种子、分层，报可判定的对数（inference-runtime 计划）。
- **可疑改写**数的是认上之后 OCR 与剧本行的相似度（取 cue 各读法的最大）低于 0.85 的 cue；`contain`（整行包含）和 `context`（夹缝认领，相似度不是判据）不在这个分布里，报数要说明。摆帧真值每素材抽 20–30 条、含一批 `contain`，判读分 right / partial / wrong / unclear（matcher 计划）。
- **疑似漏字幕判断器的漏报**按层报，每行只落第一个对得上的层；每层 ≤ 20 条全看，更大的层合计抽 20 条，报比例的 95% 上界——样本 15 条以内时"≤ 1 条真漏"只有约一半把握抓住 10% 的漏报，门槛要看点估计加上界。
  分母来自圈中的单元：一段对话在任何区域、任何一帧都没被读到时不进分母，报"漏"或"覆盖"要连这个选择偏差一起报。
  B 清单只覆盖文本包里查得到的字：原神过场字幕（`Subtitle/`）和星铁 `CutSceneCaption` 不在包里，过场短片字幕在 B 清单里无感；"文本包里有、单元没圈中"那一栏只对 ≥ 8 字的查询有效，3–7 字的会留在"文本包外"（miss-detector 计划）。
- **自选范围的每个识别组是一条独立的 OCR 线**：命中、覆盖、重复认领按该组的参照和输入范围单独报，不把几组拼成一条识别流套单组的分母；两组里出现同一句不算组内重复认领（ocr-regions 计划）。

### 归因：问"这一处发生了什么"

- 归因判据要问"这一处发生了什么"，不能问"这段文本在别处出现过没有"。短句在剧本里本就高度重复（1–2 字 84.9%、3–4 字 57.5% 有重复），
  全局模糊搜几乎必然搜得到。script-corpus 报告用全局搜得出"62% 丢在匹配器"，换成 cue 侧的非循环判据（`dev_tools/match_probe.py`）后是 0.6%。
- 位置判据用 `dev_tools/probe_gap_locate.py`，并按三档分类看。
- 匹配后的 `.ass` 文本已被换成剧本原文、时间是合成的，拿它量匹配器是循环论证（放宽阈值必然"命中"上升）。
- **淡入淡出帧上的内容行是调参权衡，不是噪音**（owner 纠正过）：强制 rec 在"空白点"读到的高分文本，抽帧一看都在屏幕上，只是对比度极低；
  "带内没有 h 30–70 的框"不等于屏幕上没字（大字号版式也会这样）。**先摆帧，再算比例。**
- 判读规则不求完备（owner 2026-09-03）：只标出"可能高价值"的轨；OCR 之后的方向是决定式清噪 → LLM 清噪（可选，还没实现）→ 合并 → 其他；不为单个病例加特判。

- **复用类改动的"打字机时间损害"拆三档报**：像素没变、读数往返（同一片像素被 rec 读成两种长度）、其余。2026-09-16 量下来真正的打字机时间损失接近 0，"伤时间"的大半是 rec 抖动（reuse-budget 计划）。
- **判叠加层（ASS 块）的改动，块数和总上屏时长一起报**：一条残读接续把静止块拖长时，块数 74 → 75，总时长却 1953.5 → 1171.0 s（matcher 计划）。

### 比臂：逐条配对，两臂量的要是同一批条目

- 各把尺各自报合计时，最容易错在"两臂量的不是同一批条目"：打字机真值上一条高误差的真值在新臂配不上，就从总账里消失、读成打平。
  比臂走 `dev_tools/evalset.py compare`：按 `(样本, 条目)` 配对，**共同集合**上比数（分母照打）、**只在一边测到的**单列、判定的转移矩阵逐格列；判定没变、数值变了的条目也逐条列出。没测到的记 `未测`，不进共同集合，也不许悄悄消失。
- 样本清单分 `regression`（被反复调参的固定回归集）和 `holdout`（按素材隔离）；**泛化结论只从 holdout 下**，回归集上的提升只说明没回退。
- 交付病例（`dev_tools/delivery_cases.py`）量的是最终 ASS 画了什么：标注时刻锚点落在框里的事件拼成整句算完整。时段按"同一段文本、首尾相接、接缝处画在同一处"的事件链算，
  "画在同一处"比的是按对齐方式（`\an`）和字号**估出**的画面范围，不是原始锚点——同一行换了对齐方式时锚点差半个行宽；一句拆成几行事件时取整句都在屏的那一段（起点取最晚的一行、终点取最早的一行）。

- **两臂命中集合不同时，摆分歧处的帧定性**，不把命中数高的一臂直接判赢（`hit_delta` 出分歧集合）；验收抽两臂之间真正变化的事件按画面标，不数"低于自己阈值的条数"（matcher 计划）。

## 追溯：产物要能追溯到是哪一版代码产的

- `build_tracks` 把 provenance（git HEAD + argv + `code_fp`）写进 `*-tracks.json`；`run_ocr2` 的 `_meta` 写 `config`（**解析后的生效值，含默认值**）和 `code_fp`（追溯用，不进复用判据）。
- `git_head()` 在 `dev_tools/` / `explore/` / `src/` 有未提交改动时缀 `+dirty`（目录表只有 `flowocr.provenance.DIRTY_PATHS` 一份）。
  改了没提交就跑，provenance 会指向一个并没有产生这份产物的 commit；**要引用表就先提交了重跑**。
- 报表比**代码指纹**（`code_fp`，产物代码的内容 hash），不比 HEAD：HEAD 移动而代码没变不误报，两棵脏树也分得开。报数前先看工具印的那行指纹 / HEAD。
- 复用判据看**解析后的生效参数**（`flowocr.extract.ocr_complete` / `ocr_args`，解析器只有一份）：第一版比命令行字面，比不出"默认值翻了"。没有 `config` 字段的旧产物一律重建。
