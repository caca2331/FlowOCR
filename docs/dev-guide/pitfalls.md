# 已知的坑

每条写清成立条件和证据入口。验证和报数的通用规矩在 [验证与报数](verification.md)。

## 时间与帧

### 时间戳比较留半个间隔的余量

任何 `t2 - t1 <= n * 标称间隔` 的判据，都要给半个间隔的余量：标称间隔是 `round()` 出来的，实测间隔会在它上下抖。
2026-09-06 `gap_frames` 的容差一微秒余量都不留（`frame_us=round(1e6/sample_fps)`，而实测采样间隔比它大 1 µs 的占 38%），
input4 的主轨 64% 是逐字重复；修完 runs 掉 66%、重复率 64% → 1%。input3 的 `sample_fps` 同样不是整数，只是 `round` 恰好落在抖动上面，侥幸没事——
"别的素材没出问题"不能作为这类判据没问题的证据。

### 容器平均帧率不是时间轴

`t_us = idx / src_fps` 的 `src_fps` 是容器的平均帧率，录像有丢帧缺口时整条时间轴被拉长（2026-09-09）：f3 两处缺口 726 帧，7.2 h 处比真实 pts 晚 9.5 s；f4 晚 5 s。
现在帧身份一律是 pts 帧号（见 [架构说明](../architecture/README.md#帧身份与解码)）。旧产物不能仅乘回 `src_fps / round(src_fps)`：缺口之后仍缺累计丢帧时长。
旧时间轴的产物不能拿来归因丢帧。

### 判"丢没丢帧"要和基准序列逐个对

窗口别只开 12 帧（2026-09-10）。硬解在 av1 上的症状原来被读成"首帧没交付、之后每隔几帧丢一帧"，那是从前 12 帧外推的；
拉到 3,600 帧和软解逐帧对照，真相是解码器启动后少交付 0–3 帧、累计错位就此封顶，之后逐字节相同，和 seek、关键帧都无关。
硬解对 h264/hevc/vp8/vp9/av1（含 film grain）全部 bit-exact；少交付发生在**前摇**里（首包 pts 为负的 av1，edit list 裁掉的那段）。
真值是**容器 pts**，不是"另一条解码路"（cv2 和 ffmpeg 软解逐格一致，错的是 NVDEC）。见 hw-decode-results 报告。

### 精确 seek 别正好落在帧的名义时刻

`-ss 帧号/帧率` 放在 `-i` 前面是精确 seek：pts 小于这个值的帧都丢掉。直播录像的 pts 常按毫秒取整（yuka input1–5：time_base 1/16000，
帧间隔 16 / 17 ms 交替），60 fps 下帧号 ≡ 2 (mod 3) 的帧比名义时刻早 0.33 ms，seek 到它的名义时刻就把它丢了（2026-09-26）。
症状是窗口第一格没交付：`--fps 2.2` 跑 yuka-f5 14843 s 窗口时首格缺失，硬解那条路还判成"吞帧"、整段退回软解；辅助流同样少了起点那一帧。
默认 2 fps 的格子帧号都是 30 的倍数、pts 精确，所以默认跑法碰不到——"默认没出过事"不能证明判据对。
现在的 seek 点退半帧（`framesource.build_ffmpeg_cmd`）；按帧号区间取帧的回抠窗口（`FfmpegWindows`）每帧核 pts，同类错会当场炸。

### 两个采样点相同，不证明中间没有字

前后两个采样点都空白、或文本相同，中间照样可能闪过一句；二分也只在谓词近似单调的边界上成立，中间有多次切换、淡入淡出或滚动时会跳过事件。
要量短暂文字的召回，得用独立的事件标注或高采样的参考臂，不能靠端点比较（decode-buffer 计划）。

### 毫秒和微秒相比要留余量

matched 产物的起止是毫秒取整（`round(x, 3)`），事件时刻是微秒；两者相比（起止对照、回抠后的夹取）严格相等会因取整差不到 1 ms 而配不上，要留至少 1 ms 余量（时间疑点计划）。

### 改了 det 的输入，回抠会被框抖带偏

涂灰、裁剪、换 det 引擎都会让同一行的框抖（自选范围的遮罩臂上，带内同文本的框 82% 挪了位置、14% 超过 6 px）。回抠链路上有三处对它敏感：
全片打字速度的样本门（不到 5 句拟得出斜率就不用）、打字机生长的框高比门（`--grow-h-ratio`）、回补的文本比较（去标点后比）。改 det 之后要看打字机真值逐项，只看整体 OCR 读数不够（ocr-regions 计划）。

## 常驻 UI 与名牌

判据在 `flowocr.analyze.uigate`，数和依据在 [defaults.md 1.25](../architecture/defaults.md#125-建轨的三个默认--ui-gate-both名牌打标--slot-reassign2026-09-20)。下面几条都栽过，都是单位或作用域上的错（ui-gate 计划）。

### 占比的分子用区间并集，分母用产物实际覆盖的跨度

逐条相加会让同一段占用随切碎程度变化：同一段 10 秒，一条 run 时占比 0.10，拆成 20 条 0.5 s 的 run 时 0.20——"换成时间就不随读法变化"当场不成立。
分母用整片时长或中位采样间隔也不对：自选范围截短的 run 不再补一格（`uigate.occupancy`）。

### 文本翻动的分母用观测数，不用 run 数

`Auto` 在 20 分钟窗里只有 4 条 run，按 run 算翻动 0.25、被门挡掉；按观测算 0.0003。覆盖率 `cover` 只对 run 级有意义，观测级恒约 1（`uigate.measure`）。

### 名牌判据要按时间分窗

整片上直接聚框位、定带、判名牌：f5 全片只聚出 1 条带，"在带上方 1~6 个字高"把 6.2 小时里落在它上方的一切都收了，挑中 10,345 条、只有 1,164 条是名字（精确率 11%）。

### 框位别用格子量化

格子的边界效应会把一个强信号切到两三个格子里，各自都不过门；按框的 IoU 聚（`uigate.footprints`）。

### 改一条用来拒某一类的判据，要拿那一类验

收紧或放宽常驻 UI 门时，要拿它本来要挡的那类（名牌、台词）验，不能只看它要剔的 UI 剔得更多还是更少。

## 匹配

### 相似度分不开此刻的台词和面板、UI 里的同一句字

一句剧本行在面板或 UI 标签里字面相同时，相似度正当地接近 1（遗器面板的标签「次元界オーナメント」对剧本行「次元界オーナメント？」）。
任何相似度阈值都分不开"此刻的台词"和"面板、UI 里的同一句字"，只能靠角色判定（面板层 + `--readables`）或时间证据（matcher 计划）。
剧本单元里的行序也是一种时间证据：短句的夹缝认领只认夹在上下两行认领之间的那一句，单独上屏的人名（地图标记、记录面板的说话人栏）落不进这个夹缝，就不会被认成"人名…？"那句台词（[defaults.md 1.67](../architecture/defaults.md#167-第五遍认领短句夹在同一单元相邻两行的认领之间2026-10-24-owner-定方向)）。

## 归因与排查

### 优化之前先 profile

任何"这里慢"的说法都要有 profile 或 A/B 端到端计时撑着。咬过两次：
①把长片的慢归给 `stitch_slots`，照着写了 50 行增量几何，实测省 0——cProfile 一跑，`dominant_text_share` 683.9 s 对 `stitch_slots` 10.0 s；
②凭直觉估"顺序解码只有 2 倍余地"差点放弃，实测局部 seek 比顺序 read 贵得多（1080p60、局部 ±150 帧：HEVC 约 35 倍、VP9 约 64 倍，关键帧间隔 250 / 281 帧；别的编码和 GOP 要另量），最后拿到 4.7 倍。

### 剖面看不见等待，等待指标不当验收

py-spy 默认不采空闲线程，等取帧、等 det、等队列在剖面里都看不见；2026-09-16 / 17 连着三次猜错病因（CPU 满、帧环太小、GIL 抢占），都是跳过了分段计时。
先看 `_meta.stage_sec` 这类同一次运行里的墙钟分段，剖面只用来看已经确定在忙的那一段。
`wait_frames`（等预取队列的时间）只用来解释瓶颈在哪，不当验收：推理越慢队列越满，等待反而下降，会把变慢读成加速。验收用固定推理配置下的端到端墙钟和 CPU / 显存（加速计划）。

### 调用数、平均批不是墙钟的代理

ORT 上组批让 rec 调用少 52%~62%，墙钟却没跟着降：量了调用数的四段里 hsr-s2、wuwa-s2、gi-s1 慢了 8%~38%，只有 yuka-f5（调用 −60%）快了 13.9%；另有 gi-s2 慢 48%（没有调用数）。慢的病因是形状池淘汰重建；Paddle 上调用少 6%，墙钟只动 6%~7%（rec 已不在关键路径）。
判快慢只看交错墙钟；调用数配上 `_meta.ort` 的 built / evicted 才分得清原因（inference-runtime 计划）。

### 旋钮声明了，不等于传到了底层

参数有声明、有解析，不等于它到了底层对象：rec 的 batch_size 曾经一直没传进 predictor，于是"批量不降本"的解释是错的（直接 A/B 的结论另算）。
量一个旋钮生不生效，先在底层对象上看它的实际值，或看 `_meta` 里的生效字段。

### 单独跑的推理延迟不能当管线里的延迟

同一个 det / rec 调用，单独跑和在管线里差 2~5 倍，而差出来的不是浪费：几路（det、两路 rec、ffmpeg 硬解）同时往一张卡上提交，单次都被拉长、总吞吐更高。
拿掉某一路让单次变快，墙钟往往不动甚至变慢（followups-evidence-0925 报告）。
判"推理这一段能省多少"，要看**同一次运行里**的等待占比（`run_ocr2 --timeline`）和端到端 A/B，不要拿单独跑的毫秒数乘调用数。

### 拿 GPU 时间线：Nsight Systems

Nsight Systems 的 `nsys` 能跟进程树（ORT 服务、ffmpeg 都抓得到）。
Windows 上 `-t` 只认 `cuda,nvtx,nvvideo,wddm…`，没有 `osrt`。**开着它管线慢约 6.5 倍**（gi-s1 60 s：38 s 对 5.8 s），所以只读 GPU 侧计时的核函数 / 拷贝时长，
调用延迟和重叠关系不能从它读。`nsys stats` 导出的 sqlite 里 `CUPTI_ACTIVITY_KIND_KERNEL` 按 `globalPid >> 24` 分进程求和、区间求并就是"卡忙了多久"。

### "某个旋钮无效"不能反推病灶在哪

2026-09-04 从"缩窗无效"推出"串联发生在窗内的 `build_regions`"，是错的：窗内区域 5,302 个、y 跨度中位数只有 0.041，
塌的是下游跨窗缝合（`stitch_slots` 判据不对称，片尾滚动表当种子吞掉全片 65% 的 run），而那一层根本不看窗长。
**把每一层的产物分别数一遍**，两个数一摆就知道是哪层塌了（clustering 报告）。

### 找到一个真缺陷 ≠ 找到这次的病因

2026-09-06 查"主轨 64% 是上一条的逐字重复"，翻出 `estimate_shift` 被重复 UI 骗到累计漂移三万像素——那确实是真缺陷，
但改完 runs 从 122,769 只掉到 122,740，重复率一点没动；真凶是上面那条 `gap_frames` 的零余量。先跑"改完没变"这条最便宜的证伪。

### 小扰动把主轨换到别的区域

一天之内四次（`--slot-span-ratio 2.0`、`--slot-geom median`、`--gap-frames 2`、`--rec-batch-size 8`），共同病根是**主轨 = 单个区域**：
丢掉的台词在两边原始观测里一字不差，是读到了、放错了地方。主轨换带不等于质量损失，要拆到真内容看（[defaults.md](../architecture/defaults.md) [§5](../architecture/defaults.md#5-一条贯穿全局的教训)）。

### 跟着推理路径走的稳定差别，先比两条路径的读数

同一处在默认路径（ORT）上逐次稳定地差、在确定性路径（Paddle）上没事，先看两边 obs 在那一刻读成了什么：rec 换了就会换字形（`っ` / `つ`、`!` / `！`、`よ` / `ょ`）。
2026-10-05 zzz-s1 一条打字机首字晚 40 帧，就是半截读成 `えっと`、整句读成 `えつと`，打字机生长的前缀比较逐字比只差这一处就过不了 0.8 的门、链断了。
拿两次读数逐字比的判据（打字机生长、回补的"文本变没变"）都要先折字形（`flowocr.textfold.fold`）或去标点（`reuse_v2.same_text`）。

## 错了不会报错的

### 自检全绿、产物是错的

- **拆开一段流程**之后，每个字段都要问它属于切开后的哪一半；只补出了问题的那条路径补不完（拆两半后有字段落错一半，窗口 8 逐框对账才看见空文本）。
- **按行区间删代码**会静默删掉一个分支，只覆盖分支内部的自检照样全绿（删 `--rec-lookahead` 时连带把 `--rec-window` 删成了空操作，是异步臂的读数抓出来的）；删代码按语法块删，并要有接线守卫（AST）和运行时计数自检。
- **批结果少返回时压缩列表**，下游 `zip` 会把后面所有结果错配到前面的框上；按下标回填（`recpool` 填 `None`）（inference-runtime 计划）。

### 等一个一定会来的东西，必须留出口

流水线里凡是"等某个一定会来的东西"的地方都要有出口，否则就是静默互等、不报错、进度停住。已经踩过四次：
帧环把已放掉的低位帧号又等回来（环记 floor）；取首帧 pts 的正则不认负号（cuvid 前摇）；批 det 的前瞻（det 批 × 采样步长）超过帧环容量；
帧环容量没装下整条管线的前瞻（取帧预取、det 批与预取、rec 窗口、回抠落后），ffmpeg 等环腾位、环等结算、结算等 ffmpeg。
帧环的容量下界和看门狗（`stall_sec`，`_meta.edge.ring_stalled`）就是为这个；卡住时看它和线程栈（`uvx py-spy dump`）（reuse-budget / decode-buffer 计划）。

## 工具与平台

### Windows 上起子进程

- 别在会起子进程的进程里阻塞读 stdin：起子进程要复制那个句柄，会死锁。
- Chocolatey 的 `ffmpeg.exe` 可能是启动器。修补烧录失败时，先停启动器，再等它启动的 FFmpeg 退出，否则 FFmpeg 仍占着临时 ASS 或输出文件。
- 别指望 Job Object 管孙进程：venv 的 `Scripts\python.exe` 是启动器，子进程会静默逃出去。收尾要按进程树（ppid 闭包）确认清空。
- 共享推理服务靠 `--exit-on-stdin-eof` 自退出，不是拿 pid 探活：Windows 上句柄没释放就探不出死活。
- 停任务后核一遍进程树：有一次以为是"别人的负载"的 11.5 GB 里，有 3.7 GB 是自己的孤儿进程。

### ffmpeg 与管道

- ffmpeg 要 `-nostats`：进度行以 `\r` 结尾，会粘住下一行 showinfo。
- 管道里的 `grep` / `sed` / `awk` 写文件时块缓冲，一律加 `--line-buffered`（见 [开发指南](README.md#长任务的纪律)）。

选帧别用 `-vf fps=N`：它是补帧 / 丢帧滤镜，缺口处复制帧填上，有 pts 缺口的录像上会凭空造出观测；用 `select` 按帧号选、加 `-fps_mode passthrough`。
`-hwaccel cuda` 要配 `-hwaccel_output_format cuda`，否则每帧下载回内存（`framesource` 文件头）。
烧叠加 ASS 到某一时刻的帧时，`-ss` 放在 `-i` 前面会把输出时间轴归零，`subtitles` / `ass` 滤镜按 t≈0 画——每张图都"看着正常"、其实是片头那块；要加 `-copyts`（matcher 计划）。

### 别把 CUDA 库目录塞进 `PATH`

2026-09-22（换 CUDA 13 时，cuDNN 9.13）把 pip 装的 CUDA 库目录塞进了 `PATH`：`PATH` 被 ORT 子进程继承，cuDNN 于是找得到 NVRTC，EXHAUSTIVE 搜索把运行时编译的引擎也算进来，
每个新形状第一次 run 从约 0.15 s 变成约 2 s，稳态不变——每形状一个 session 的管线上 ORT 推理时间涨 2.3~4.5 倍。现在只预载 DLL（`ort.preload_dlls()`）、不动 `PATH`。
用户自己的 `PATH` 里本来就有 CUDA Toolkit（带 NVRTC）时可能再现，现行 ORT 1.29 上没实测；首个形状特别慢时先查这个（project-structure 账本（已删；归档的 project-structure 计划开头写了怎么回查））。

### Bash 与 PowerShell

- 别改正在运行的 shell 脚本：bash 边读边执行（2026-09-06 `head2head.sh` 跑到一半被改，五部跑完后以 `unexpected EOF` 退出码 2 收场，数据没坏、退出码和日志在骗人）。
- 读正在被写的文件大小用 bash 的 `stat`；PowerShell 目录枚举对一个 77 MB 的文件报过 0 字节。

### ORT 的动态形状

ORT 每次形状变化都重规划，所以 rec 的宽度收到 320 的倍数、每个形状一个 session（`--per-shape`）。
rec 的右侧补零有剂量反应（2026-09-21）：多补 ≤320 列是噪声，+480 列起明显变差，所以宽度网格 320 不能再粗；批维随便（读数只差噪音级）。
分桶宽由后端的 `shape_w` 一处决定。

显存随形状数涨多少取决于 session 之间共不共用显存（[推理服务](../architecture/README.md#推理服务)）：默认共用 arena 和权重，每个形状约 50 MB；
关掉共用（`--no-ort-share-mem`）或探针自己起的服务没开 `--share-mem 1` 时，每个 session 各自一份 arena，线性涨——一次扫 24 个形状实测吃到 15 GB。
扫宽 × 批的探针要拆成几次跑，跑之前先看 `nvidia-smi`。
