# 已知的坑

每条写清成立条件和证据入口。验证和报数的通用规矩在 [验证与报数](verification.md)。

## 时间与帧

### 时间戳比较留半个间隔的余量

任何 `t2 - t1 <= n * 标称间隔` 的判据，都要给半个间隔的余量：标称间隔是 `round()` 出来的，实测间隔会在它上下抖。
2026-09-06 `gap_frames` 的容差一微秒余量都不留（`frame_us=round(1e6/sample_fps)`，而实测采样间隔比它大 1 µs 的占 38%），
input4 的主轨 64% 是逐字重复；修完 runs 掉 66%、重复率 64% → 1%。input3 的 `sample_fps` 同样不是整数，只是 `round` 恰好落在抖动上面，侥幸没事——
"别的素材没出问题"不能作为这类判据没问题的证据。

### 容器平均帧率不是时间轴

`t_us = idx / src_fps` 的 `src_fps` 是容器的平均帧率，录像有丢帧缺口时整条时间轴被拉长（2026-09-09）：f3 两处缺口 726 帧，7.2 h 处比真实 pts 晚 9.5 s；f4 晚 5 s。
现在帧身份一律是 pts 帧号（见 [架构说明](../architecture/README.md#帧身份与解码)）。旧产物不能仅乘回 `src_fps / round(src_fps)`：缺口之后仍缺累计丢帧时长。
旧时间轴的产物不能拿来归因丢帧。

### 判"丢没丢帧"要和基准序列逐个对

窗口别只开 12 帧（2026-09-10）。硬解在 av1 上的症状原来被读成"首帧没交付、之后每隔几帧丢一帧"，那是从前 12 帧外推的；
拉到 3,600 帧和软解逐帧对照，真相是解码器启动后少交付 0–3 帧、累计错位就此封顶，之后逐字节相同，和 seek、关键帧都无关。
硬解对 h264/hevc/vp8/vp9/av1（含 film grain）全部 bit-exact；少交付发生在**前摇**里（首包 pts 为负的 av1，edit list 裁掉的那段）。
真值是**容器 pts**，不是"另一条解码路"（cv2 和 ffmpeg 软解逐格一致，错的是 NVDEC）。见 hw-decode-results 报告。

### 精确 seek 别正好落在帧的名义时刻

`-ss 帧号/帧率` 放在 `-i` 前面是精确 seek：pts 小于这个值的帧都丢掉。直播录像的 pts 常按毫秒取整（yuka input1–5：time_base 1/16000，
帧间隔 16 / 17 ms 交替），60 fps 下帧号 ≡ 2 (mod 3) 的帧比名义时刻早 0.33 ms，seek 到它的名义时刻就把它丢了（2026-09-26）。
症状是窗口第一格没交付：`--fps 2.2` 跑 yuka-f5 14843 s 窗口时首格缺失，硬解那条路还判成"吞帧"、整段退回软解；辅助流同样少了起点那一帧。
默认 2 fps 的格子帧号都是 30 的倍数、pts 精确，所以默认跑法碰不到——"默认没出过事"不能证明判据对。
现在的 seek 点退半帧（`framesource.build_ffmpeg_cmd`）；按帧号区间取帧的回抠窗口（`FfmpegWindows`）每帧核 pts，同类错会当场炸。

## 归因与排查

### 优化之前先 profile

任何"这里慢"的说法都要有 profile 或 A/B 端到端计时撑着。咬过两次：
①把长片的慢归给 `stitch_slots`，照着写了 50 行增量几何，实测省 0——cProfile 一跑，`dominant_text_share` 683.9 s 对 `stitch_slots` 10.0 s；
②凭直觉估"顺序解码只有 2 倍余地"差点放弃，实测局部 seek 比顺序 read 贵 34 倍，最后拿到 4.7 倍。

### 单独跑的推理延迟不能当管线里的延迟

同一个 det / rec 调用，单独跑和在管线里差 2~5 倍，而差出来的不是浪费：几路（det、两路 rec、ffmpeg 硬解）同时往一张卡上提交，单次都被拉长、总吞吐更高。
拿掉某一路让单次变快，墙钟往往不动甚至变慢（followups-evidence-0925 报告）。
判"推理这一段能省多少"，要看**同一次运行里**的等待占比（`run_ocr2 --timeline`）和端到端 A/B，不要拿单独跑的毫秒数乘调用数。

### 拿 GPU 时间线：Nsight Systems

Nsight Systems 的 `nsys` 能跟进程树（ORT 服务、ffmpeg 都抓得到）。
Windows 上 `-t` 只认 `cuda,nvtx,nvvideo,wddm…`，没有 `osrt`。**开着它管线慢约 6.5 倍**（gi-s1 60 s：38 s 对 5.8 s），所以只读 GPU 侧计时的核函数 / 拷贝时长，
调用延迟和重叠关系不能从它读。`nsys stats` 导出的 sqlite 里 `CUPTI_ACTIVITY_KIND_KERNEL` 按 `globalPid >> 24` 分进程求和、区间求并就是"卡忙了多久"。

### "某个旋钮无效"不能反推病灶在哪

2026-09-04 从"缩窗无效"推出"串联发生在窗内的 `build_regions`"，是错的：窗内区域 5,302 个、y 跨度中位数只有 0.041，
塌的是下游跨窗缝合（`stitch_slots` 判据不对称，片尾滚动表当种子吞掉全片 65% 的 run），而那一层根本不看窗长。
**把每一层的产物分别数一遍**，两个数一摆就知道是哪层塌了（clustering 报告）。

### 找到一个真缺陷 ≠ 找到这次的病因

2026-09-06 查"主轨 64% 是上一条的逐字重复"，翻出 `estimate_shift` 被重复 UI 骗到累计漂移三万像素——那确实是真缺陷，
但改完 runs 从 122,769 只掉到 122,740，重复率一点没动；真凶是上面那条 `gap_frames` 的零余量。先跑"改完没变"这条最便宜的证伪。

### 小扰动把主轨换到别的区域

一天之内四次（`--slot-span-ratio 2.0`、`--slot-geom median`、`--gap-frames 2`、`--rec-batch-size 8`），共同病根是**主轨 = 单个区域**：
丢掉的台词在两边原始观测里一字不差，是读到了、放错了地方。主轨换带不等于质量损失，要拆到真内容看（[defaults.md](../architecture/defaults.md) [§5](../architecture/defaults.md#5-一条贯穿全局的教训)）。

## 工具与平台

### Windows 上起子进程

- 别在会起子进程的进程里阻塞读 stdin：起子进程要复制那个句柄，会死锁。
- 别指望 Job Object 管孙进程：venv 的 `Scripts\python.exe` 是启动器，子进程会静默逃出去。收尾要按进程树（ppid 闭包）确认清空。
- 共享推理服务靠 `--exit-on-stdin-eof` 自退出，不是拿 pid 探活：Windows 上句柄没释放就探不出死活。
- 停任务后核一遍进程树：有一次以为是"别人的负载"的 11.5 GB 里，有 3.7 GB 是自己的孤儿进程。

### ffmpeg 与管道

- ffmpeg 要 `-nostats`：进度行以 `\r` 结尾，会粘住下一行 showinfo。
- 管道里的 `grep` / `sed` / `awk` 写文件时块缓冲，一律加 `--line-buffered`（见 [开发指南](README.md#长任务的纪律)）。

### Bash 与 PowerShell

- 别改正在运行的 shell 脚本：bash 边读边执行（2026-09-06 `head2head.sh` 跑到一半被改，五部跑完后以 `unexpected EOF` 退出码 2 收场，数据没坏、退出码和日志在骗人）。
- 读正在被写的文件大小用 bash 的 `stat`；PowerShell 目录枚举对一个 77 MB 的文件报过 0 字节。

### ORT 的动态形状

ORT 每次形状变化都重规划，所以 rec 的宽度收到 320 的倍数、每个形状一个 session（`--per-shape`）。
rec 的右侧补零有剂量反应（2026-09-21）：多补 ≤320 列是噪声，+480 列起明显变差，所以宽度网格 320 不能再粗；批维随便（读数只差噪音级）。
分桶宽由后端的 `shape_w` 一处决定。

显存随形状数涨多少取决于 session 之间共不共用显存（[推理服务](../architecture/README.md#推理服务)）：默认共用 arena 和权重，每个形状约 50 MB；
关掉共用（`--no-ort-share-mem`）或探针自己起的服务没开 `--share-mem 1` 时，每个 session 各自一份 arena，线性涨——一次扫 24 个形状实测吃到 15 GB。
扫宽 × 批的探针要拆成几次跑，跑之前先看 `nvidia-smi`。
